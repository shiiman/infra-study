## 問1 — 答え: **B**

**組織 → フォルダ → プロジェクト**

- 上位で付けた権限は下位に継承される
- AWS の Organizations → OU → アカウント とほぼ同じ構造
- ただし GCP は**プロジェクトが標準の器**で、AWSのようにアカウントを分けなくてよい

→ 第1回

## 問2 — 答え: **C**

そのバケットに `roles/storage.objectViewer` を付与する。

- **A** `roles/owner` は何でもできる。論外
- **B** `roles/storage.admin` はプロジェクト内の**全バケット**を操作できてしまう

## 問3 — 答え: **B と C**

- **B** VPC はグローバル
- **C** サブネットはリージョン

AWS では「VPCはリージョン、サブネットはAZ」でした。**1段ずつ広い**のが GCP です。

- **A** VPC はリージョンではない
- **D** サブネットはゾーンではない(AWSのAZ感覚だと間違えやすい)
- **E** `auto_create_subnetworks = false` にすれば作られない

→ 第2回

## 問4 — 答え: **B**

Cloud Router と Cloud NAT を作る。

- **A** Private Google Access は **Google API** へ到達するためのもの。
  インターネット全体には出られない
- **C** 外部IPを付ければ出られるが、「外部IPを持たない」という前提を壊している
- **D** GCP の egress は既定で全許可。Firewall では解決しない

**第2回で NAT より先に Private Google Access を教えた理由**がここ。
逆順だと NAT 経由で到達できてしまい、PGA の効果が見えません。

→ 第2回

## 問5 — 答え: **B**

ネットワークタグまたはサービスアカウントで対象を指定する。

- **A** GCP では**他の Firewall ルールを送信元にできない**。
  AWS の「SGからSGへ」ができないのが最大の差分
- **C** Firewall ルールは VPC 単位。タグ/SAで対象を絞る
- **D** egress ルールはある(既定で全許可)

→ 第2回

## 問6 — 答え: **A と C**

- **A** `35.235.240.0/20` は IAP の固定レンジ
- **C** `roles/iap.tunnelResourceAccessor` が無いとトンネルを張れない

**「ネットワークの許可」と「IAM の許可」の2層**が揃って初めて通ります。

- **B** `0.0.0.0/0` は開けすぎ
- **D** IAP を使えば踏み台は要らない(第2回の主題)
- **E** 外部IPは不要

**切り分けのコツ**
タイムアウト = ネットワーク、権限エラー = IAM。

## 問7 — 答え: **B**

Firewall ルールで `130.211.0.0/22` と `35.191.0.0/16` を許可していない。

**503 は「健全なバックエンドが無い」という意味**です。
ロードバランサは VPC の外にいるので、Firewall で止められると
ヘルスチェックが通らず、バックエンドが不健全と判定されます。

- **A** アプリのエラーなら **502**(バックエンドが変な応答を返した)
- **C** DNS の問題なら、そもそも繋がらない
- **D** 証明書未発行なら TLS のエラーになる

**503 と 502 の違い**は覚えておくと切り分けが速くなります。

→ 第3回

## 問8 — 答え: **A**

Spanner は Google API 経由、Memorystore は VPC 内にあるため。

第4回でやった**3種類の接続方式**です。

| 方式 | サービス | 必要な準備 |
|---|---|---|
| Google API 経由 | Spanner / BigQuery / Cloud Storage | Private Google Access |
| VPCピアリング | Cloud SQL / Memorystore | 限定公開サービスアクセス |
| Auth Proxy | Cloud SQL(別解) | プロキシの起動 |

Cloud Run は **VPC の外**で動くので、Google API には繋がるが
VPC 内のものには繋がりません。Direct VPC egress で解決します(第5回)。

→ 第4回 / 第5回

## 問9 — 答え: **C**

限定公開サービスアクセス(VPCピアリング)。

グローバルアドレスを予約して Google に貸し出し、
サービスネットワーキング接続を張ります。

**CIDR は `/24` では足りません。**
制作時の検証で `/24` にしたら
`Couldn't find free blocks in allocated IP ranges` で失敗しました。
`/20` 以上にしてください。

→ 第4回

## 問10 — 答え: **A**

`min_instance_count` を 0 にする。

- リクエストが無い間はインスタンスが0になり、課金されない
- ただし次のリクエストで**コールドスタート**が発生する
- レイテンシが気になるなら 1 以上にするが、その分は常に課金される

- **B** `max_instance_count = 0` はスケールできなくなる(設定として不正)

→ 第5回

## 問11 — 答え: **B**

ロードバランサのバックエンドに付ける機能である。

**CloudFront との一番大きな違い**です。

| | CloudFront | Cloud CDN |
|---|---|---|
| 位置づけ | 独立したサービス | ロードバランサの機能 |
| 作るもの | ディストリビューション | `enable_cdn = true` |
| 証明書 | ACM(us-east-1限定) | LBの証明書をそのまま |

第3回で作ったロードバランサに配信先を1つ足すだけで済みます。

→ 第6回

## 問12 — 答え: **B**

`allUsers` に `roles/storage.objectViewer` を付与する。

- **A** GCP のバックエンドバケットには **OAI に相当する仕組みが無い**。
  ここは AWS のほうが細かく制御できます
- **C** 非公開のままだと Cloud CDN も読めず、403 になります
- **D** 署名付きURLは別の配信方法。バックエンドバケットの要件ではない

**副作用**
バケットが誰でも直接読める状態になります。
Cloud Armor を付けても `storage.googleapis.com` への直アクセスは素通しです
(第6回 宿題3)。

→ 第6回

## 問13 — 答え: **A と B**

- **A** `roles/run.developer` — デプロイ先を更新する権限
- **B** `roles/iam.serviceAccountUser` — 実行SAになりすます権限

**1つ目だけでは通りません。** ここが第7回の山場でした。

デプロイするということは「そのサービスアカウントの権限で動くものを作る」
ということなので、そのSAを使ってよいという許可が別に要ります。
AWS の `iam:PassRole` と同じ考え方です。

- **C** ストレージは関係ない
- **D** イメージを **push** するので `writer` が要る。`reader` では足りない
- **E** ビルドを動かす側の権限。デプロイには関係ない

→ 第7回

## 問14 — 答え: **B**

`lifecycle { ignore_changes = [template[0].containers[0].image] }` を書く。

**インフラの形は Terraform、動かすバージョンは CI/CD。**
その境界を1ブロックで宣言します。

- **A** 管理から外すと、他の設定も追えなくなる
- **C** CI/CD から Terraform を回す構成もあるが、この問題の解にはならない
- **D** 運用でカバーするのは解決ではない

**注意**: `ignore_changes` を広げすぎないこと。
入れた属性は Terraform が管理をやめるので、コードと実物のズレが plan に出なくなります。

→ 第7回

## 問15 — 答え: **C**

サイトが外から見えなくなった。

**鳴らす基準は「鳴ったら人が何かするか」だけ**です。

- **A** CPU 使用率が高いこと自体では何もしない。
  「CPUが高くて応答が遅い」なら、**遅いほう**を鳴らす
- **B** リクエストが多いのは障害ではない
- **D** 同上

**症状を鳴らす。原因はダッシュボードとログで調べる。**
見ても何もしないものはダッシュボードに置きます。

→ 第8回
