### Q1. 今日は第何回でしたか(必須・プルダウン)

第1回〜第9回

### Q2. 今日やったことを、同僚に説明できそうですか(必須・ラジオ)

> 補足文: 「いちばん知りたい設問です。正直に選んでください。」

- 説明できる
- だいたい説明できる
- **手順は再現できるが、なぜそうするかは説明できない**
- 説明できない

> **★ この設問がこのアンケートの中心。**
> 理解度を「わかった/わからない」ではなく**行動**で測る。
>
> **3番目が多かったら、その回は失敗**とみなす。
> この勉強会は「なぜ繋がらないか」を教えるのが軸なので、
> 手順だけ再現できても意味がない。

### Q3. 難易度はどうでしたか(必須・5段階)

`1 = 簡単すぎた` 〜 `5 = 難しすぎた`(3がちょうどよい)

### Q4. ハンズオンは時間内に最後まで終わりましたか(必須・ラジオ)

- 終わった
- 終わったが、ぎりぎりだった
- 途中までしかできなかった
- ほとんど手を動かせなかった
- ハンズオンがない回だった

> 「時間は足りたか」という**主観**ではなく、**事実**を聞く。
> 「途中までしかできなかった」が何人いるかで、次回の尺を判断できる。

### Q5. 「作る → 繋がらない → 理由を知る → 通す」という進め方は、理解の役に立ちましたか(必須・ラジオ)

> 補足文: 「この勉強会がずっと採っている進め方です。合っているか毎回確認しています。」

- とても役に立った / 役に立った / どちらでもない / まわりくどいと感じた / 今日はその流れが無かった

> **設計の核心を毎回測る。** 全体アンケートだけだと、
> どの回で機能しなかったのかが分からない。

### Q6. 今日の内容は、自分の仕事で使えそうですか(必須・ラジオ)

- すぐ使えそう / いずれ使いそう / 今の担当では使わなそう / 判断できない

> AWS版アンケートの「インフラの設計についてはまだ理解が及ばなかった」
> という声を**早期に拾う**ための設問。

### Q7. わからないまま終わったこと、つまずいた箇所があれば教えてください(任意・記述)

> 補足文で具体例を示している(「applyが通らなかった」など)。
>
> **次回の冒頭で拾う。** 同じ箇所が複数人から挙がったら、その回の資料を直す。

## 設問を改訂した経緯(2026-08-31)

初稿は定番の設問(難易度 / 時間 / スピード / 自由記述4つ)だったが、
**「難しかった」と言われても何を直せばいいか分からない**という弱さがあった。
改善アクションに直結する聞き方に変えた。

| 変更 | 理由 |
|---|---|
| 「説明のスピード」を削除 | 難易度と相関が高く、情報が重複する |
| **「同僚に説明できそうか」を追加** | 理解度を行動で測る。「手順は再現できるが理由は説明できない」を選択肢に入れて、教材の失敗を検知できるようにした |
| 「時間は足りたか」→「時間内に最後まで終わったか」 | 主観より事実 |
| **「作る→繋がらない→通す」を各回で聞く** | 設計の核心。全体だけだとどの回で機能しなかったか分からない |
| **「自分の仕事で使えそうか」を追加** | AWS版の「設計は理解が及ばなかった」という声を早期に拾う |
| 自由記述 4つ → 2つ | 「1分で終わる」を守るため。「わからないまま」と「つまずいた箇所」を統合 |

全体アンケートには次を追加した。

- **Q2 一から組めそうか** — 勉強会のゴールそのものを直接聞く
- **Q8 勉強会がなかったら学んでいたか** — 形式の必要性
- **Q11 開催ペース** / **Q12-13 宿題** — 運営の判断材料
- **Q17 次に扱ってほしいテーマ** — 次回企画の入口
